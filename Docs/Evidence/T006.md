### 1.1 一个实测到的导出行为（改了作者参数以适配它）

第一次导出得到 **1.041667 s**（= 25/24）。读导出器源码
`gltf2_blender_gather_animation_sampler_keyframes.py`（采样循环 `while frame <= end_frame`）确认：
**它写的是绝对时间 `frame / fps`**，所以帧 1→25 会写成 0.0417→1.0417（跨度对、但起点不在 0）。

**处理**：把动作改成**帧 0 → 帧 24**（24 fps）⇒ 文件里的时间恰为 **0.000 → 1.000 s**。
这不改产品规则，只是让导出文件的时间轴起点与长度都干净。

### 1.2 尺寸链路（与 T005 一致）

| | Blender（米） | Godot（米，实测） |
|---|---|---|
| 网格 AABB 尺寸 | (0.20, 0.60, 0.44) | **(0.20, 0.44, 0.60)** ✓ 符合 `(x,y,z)→(x,z,−y)` |
| 网格 AABB 角点 | min (−0.10, −0.30, 0.0) | **(−0.10, 0.0, −0.30)** |
| 骨骼静止头位置 | `spine` (0,−0.30,0.34) | **(0, 0.34, 0.30)** |
| | `leg_front` (0,0.20,0.24) / `leg_back` (0,−0.20,0.24) | **(0, 0.24, −0.20) / (0, 0.24, 0.20)** |

> **AABB 角点的坑（实测踩到）**：轴翻转下 **"最小角"不映射成"最小角"**。
> Blender 的 y∈[−0.30,0.30] 经 `z_g = −y_b` 变成 z_g∈[−0.30,0.30]，其**最小角对应 Blender 的最大 y 角**。
> 所以断言不能把角点按 `(x,z,−y)` 直接换算，必须**整段区间映射后取 min**（Godot 实测值 (−0.10, 0.0, −0.30)）。

### 3.1 "真的在动"与"循环闭合"的关键数据

| 采样 | `leg_front` 骨方向 | `leg_back` 骨方向 |
|---|---|---|
| t=0.0 | `(0, −1, 0)`（竖直向下） | `(0, −1, 0)` |
| t=0.5 | `(0, −0.8148, −0.5798)`（向后摆 35.4°） | `(0, −0.9162, +0.4007)`（向前摆 23.6°） |
| t=1.0 | `(0, −1, 0)`（回到 t=0，闭合误差 0.000°／0.000 mm） | `(0, −1, 0)` |

- 脚端位移：前腿 **0.1756 m**、后腿 **0.0918 m** → 不是"文件里有个动画名"，是真在动。
- 世界方向变化（35.43°/23.62°）**不等于**作者写的 ±30°，因为腿是 `spine` 的子骨，
  **叠加了 spine 的 6°**；所以精确断言写在**动画轨道的作者数值**上（峰值 29.528°，见 3.2），
  世界方向只做区间断言。

### 3.2 "作者 30° → 导入后 29.53°"：一个真实的导入行为（已定量）

Godot 导入时按 `animation/fps`（默认 **30**）重采样，并**丢掉部分键**。实测键时间：

```
0.0000, 0.0333, ..., 0.4667, [0.5 缺失], 0.5333, ..., 0.9667, 1.0000   （30 键，末键被吸到 1.0）
```

于是 t=0.5（源里帧 12 的峰值 30°）**不是键**，两侧最近键各为 **29.528°** → 峰值损失 **1.6%**。

又实测把 `animation/fps` 改成 **24**（与源一致）后：键变成 22 个且**丢掉 0.25/0.5/0.75**，
峰值反而更低（**29.410°**）→ **恢复为 Godot 默认 30 fps**（略优），并把该限制记录在案：

> **已知限制**：源里落在重采样网格之间的极值会被削掉约 1–2%。若将来动作幅度敏感，
> 要么提高 `animation/fps`，要么在源里让极值落在采样点上，或改用 `AnimationTree` 侧处理。
> 本任务的动作幅度 30° → 29.53° 属可接受范围（验收容差 1.0°）。
