## 4. 能力门实测（**先量再写规格**，Godot 4.7 口径）

| 实测 | 结论 / 依据 |
|---|---|
| 烘焙源几何 | `NavigationRegion3D.bake_navigation_mesh(false)` 只认 **`geometry_source_geometry_mode`** 指定的源：<br>`ROOT_NODE_CHILDREN` = **区域自己的子节点**（把几何放在区域兄弟节点上烘出 **0 面**）；<br>最终用 **`GROUPS_WITH_CHILDREN` + 分组名 `nav_source_courtyard`**，让**两张图烘同一套几何** ✓ |
| 烘焙格 cell | 在一个"0.24 缝 + 两段墙"的试验场上扫描：**cell 0.03 时鼠路径直穿缝（长度 = 直线 6.00 m）**；cell 0.05/0.10 时缝被吃掉、路径改绕行（6.19–6.32 m） |
| `region_min_size` | 太小会退化：`cell 0.05 + rmin 0.05` 实测**查询恒空**（等 60 帧无路径）；`cell 0.03 + rmin 0.02` 正常。故取 cell 0.03 / rmin 0.02 |
| 地图格必须与导航面一致 | 不一致会刷 `cell size mismatch … rasterization errors`。已在 `project.godot` 加 `[navigation] 3d/default_cell_size/height = 0.03`，断言也核对 `map_get_cell_size == navmesh.cell_size` |
| **运行期换 navmesh 后同进程查询不可靠** | 工具里给 region 换 navmesh 再烘，**同进程等 600 帧仍 0 路径点**；**落盘 `.tres` 后新进程加载**则第 **1** 帧就能取到路径。<br>→ 因此：工具只"烘焙 + 落盘 + 赋回场景"，路径与行走断言放在**独立进程**的 `run_t012_navigation.gd`（也顺带保证"测的是真正落盘的数据"） |
| API 名 | `NavigationMesh` **没有** `navigation_layers`（分层在 `NavigationRegion3D` / `NavigationAgent3D` 上）；`map_get_closest_point(map, p)` **只有 2 个参数**（不吃 layer）；`PARSED_GEOMETRY_STATIC_COLLIDERS = 1`；`SOURCE_GEOMETRY_GROUPS_WITH_CHILDREN` 与 `geometry_source_group_name` 生效 |
| 导航调试绘制 | `NavigationServer3D.set_debug_enabled(true)` 调用成功、**但运行时画面里没有画出来**（见 §6） |

## 6. 视觉证据：**NOT-RUN**（已如实记录）

- 按 T011 的做法给捕获工具加了 `-- t012`：加载关卡 → `NavigationServer3D.set_debug_enabled(true)` → **按层分别只开一个 region**
  （`NavRegion_Mouse.enabled` / `NavRegion_Cat.enabled`）→ 在树根屏障与溪缝上方各拍一张。
- 结果：**鼠/猫两张图的 MD5 逐字节相同**（`t012_tree_hole_mouse.png` 与 `..._cat.png` 同为 `E79CF026E8…`；
  `t012_creek_gap_*` 同为 `F73CADFA45…`，`unique_colors` 也一致 220/220、597/597）→ **导航面没有被画出来**。
- **结论：本环境下"引擎运行时导航调试绘制"不可得 → T012 的视觉证据记 NOT-RUN**，不提交这 4 张重复图（避免噪声），
  **不以任何方式编造画面判断**。证据改用：① 结构判据（洞里有没有导航面）② 分层路径矩阵 ③ 真实胶囊逐帧行走。

## 7. 过程中修掉的判定口径（都是"断言写错"，不是产品参数）

| 问题 | 根因 | 处置 |
