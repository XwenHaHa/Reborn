## 2. 发现的渲染缺陷（T002/T007 视觉项原本是坏的）

### 2.1 现象

对 T007 导出程序的窗口截图做分析，报告：

> 画面**不是**正常渲染的。客户端区域呈现为**纯黑（略带深灰/深蓝色调）的空白**，
> 没有任何渲染输出……整个游戏窗口客户区是纯色空白。

### 2.2 根因（核对场景文件确认）

`scenes/maps/l_movement_lab.tscn` 存在**三个缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | **完全没有光源**（无 `DirectionalLight3D` / `OmniLight3D`） | 所有网格无光照 → 渲染为黑 |
| 2 | **没有 `WorldEnvironment`** | 无环境光/天空，背景只剩 `default_clear_color`(0.15,0.17,0.2) |
| 3 | `Camera3D` **未设 `current = true`** | 依赖引擎自动分配 |

那个"深灰蓝"正是我设的 `default_clear_color`，与报告的描述完全吻合。

**这说明**：T002 的 18 条断言（尺寸、出生、碰撞、落地）**全部正确**，但**场景在视觉上不可用**。
数值断言覆盖不了"有没有光、相机是否激活、能不能看见东西"。

### 2.3 修复

新增 `res://tests/tool_edit_lab_scene.gd`（一次性场景修补工具），
用**引擎常量**构造节点、由引擎自己序列化（避免手写 `.tscn` 猜枚举值）：

- `SunLight`：`DirectionalLight3D`，`rotation_degrees=(-45,-35,0)`，`light_energy=1.2`，`shadow_enabled=true`
- `WorldEnvironment`：`Environment` + `ProceduralSkyMaterial` + `Sky`，
  `background_mode=BG_SKY`(2)、`ambient_light_source=AMBIENT_SOURCE_SKY`(3)、`tonemap_mode=TONE_MAPPER_FILMIC`(2)
  （**这三个数字是引擎运行时打印出来的**，不是猜的）
- `Camera3D.current = true`
- 区分材质：地面 `#52575c`、标尺 `#e6b82e`、方向标记 `#2e9ed9`

## 3. 修复过程中的两个真实 bug

### 3.1 工具把运行时状态烧进了场景文件（严重）

**第一版工具**的做法是：`instantiate()` → `root.add_child()` → `await process_frame` → `pack()` → 保存。

**后果**：入树会执行 `_ready()` 并让物理生效，而 `PackedScene.pack()` 捕获的是**运行时状态**。
`l_movement_lab.tscn` 里的 Player 被写成了：

```
[node name="Player" type="CharacterBody3D" ...]
transform = Transform3D(1, 0, 0, 0, 1, 0, 0, 0, 1, 0, 1.4210554, 0)   ← 已下落 7.9cm
velocity = Vector3(0, -1.1433334, 0)                                    ← 下落瞬时速度
```

**发现方式**：T002 的 `player_at_start_m` **稳定失败**（实测 0.0789 m，恰好等于 1.5 − 1.4210554）。

**修正原则**（已写入工具注释）：
> **场景编辑工具绝不能把场景加进场景树。**
> 全程在未入树的实例上操作：方向光/环境/材质都不需要入树；
> `Camera3D.current` 在实例上设标志位也会被正确序列化。

并加了**"无意外变更"自检**：编辑前后比对 `Player`/`PlayerStart`/`Ground`/`Camera3D`
的 transform 与 `Player.velocity`，变化即报错。实测输出：

```
TOOL|unchanged|Player|OK
TOOL|unchanged|PlayerStart|OK
TOOL|unchanged|Ground|OK
TOOL|unchanged|Camera3D|OK
TOOL|unchanged|Player.velocity_is_zero|OK (actual (0.0, 0.0, 0.0))
```

### 3.2 自发光反而破坏了立体感

为提高对比度，第一版给物体加了 `emission=0.25`。vision 复核报告：

> 立方体各面颜色几乎一致，立体感很弱，物体看起来像"浮"在地面上

**自发光把方向光造成的明暗差冲掉了。** 去掉自发光后：

> 可以清晰看到立方体的顶面亮度最高，左侧面次之，右侧面最暗。

**教训**：区分物体应靠**反照率颜色 + 方向光**，不该用自发光。

### 3.3 T002 断言的时序脆弱（顺带修掉）

原 `player_at_start_m` 读的是**运行中正在下落的玩家位置**，断言前跑了几个物理帧取决于
渲染开销——加光源/阴影后从 `0.0000` 变成 `0.0789`。

**修正**：把该断言拆成两部分
- `player_authored_at_start_m`：在**入树之前**比较**局部位置**（实例化后即可读，完全确定）；
- `authored_spawn_above_ground`：作者摆放高度保证胶囊底 ≥ 地面顶面；
- 重叠检测改用**不动的 `PlayerStart.global_position`**，不再用会漂移的玩家位置。

## 4. 最终验证结果

### 4.1 客观像素统计（引擎自绘，非屏幕截图）

**为什么不用屏幕截图**：屏幕截图依赖窗口可见/在前台/未被遮挡/DPI 正确。实测中游戏窗口
会处于 `(-25600,-25600)` 且客户区 `0x0`（Windows 最小化位置），截到的是桌面背景，
导致两次视觉分析结论**互相矛盾**。

改为由引擎导出 viewport 纹理（`tests/tool_capture_render.gd`，需**非 headless** 运行）：

```
CAP|viewport_size=(1280.0, 720.0)
CAP|active_camera=Camera3D
CAP|camera_global_pos=(0.0, 0.540195, 0.0)|global_rot_deg=(0.0, 0.0, 0.0)|fov=90.0
CAP|image_size=1280x720
CAP|stats|sampled=102480|unique_colors=2151
CAP|stats|lum_min=0.3089|lum_max=0.8865|lum_mean=0.5801|range=0.5776
CAP|stats|clear_color_like_ratio=0.0000
```

| 指标 | 值 | 含义 |
|---|---|---|
| `active_camera` | `Camera3D` | 相机确实激活 |
| `unique_colors` | **2151** | 有真实内容，非纯色 |
| 亮度范围 | **0.5776** | 有明显明暗结构 |
| **`clear_color_like_ratio`** | **0.0000** | **无一个像素是旧的空白深色** |

### 4.2 视觉判断（vision.js，对引擎导出的帧）

| 问题 | 回答 |
|---|---|
| 地面上黄条与青蓝立方体是否清晰可辨？ | **是**，颜色鲜明、边缘锐利 |
| 立方体是否有明暗面（立体感）？ | **是**，顶面最亮、左侧次之、右侧最暗 |
| 地平线在高度百分之几？ | **约 50%** |
| 有无投射阴影？ | **无**（见 §5） |
| 整体画面质量？ | 正常的简单测试场景，透视/光照/渐变天空均正常，无破面/撕裂/报错 |

**地平线在 50% 与几何计算一致**：相机在 `y=0.54` 平视，视平线即画面中线。
**画面中只有地面 + 两个标记物、看不到其它几何体也与几何一致**：标尺 `(1.2,0.11,-2.5)`
与方向标记 `(0.6,0.11,-1.2)` 才算进入 90° FOV 视野内（原先放在 `x=3`/`x=1.5`、`z=0`，
相对相机是 90° 正侧方，**在视野之外**，因此顺手挪到了前方）。

## 5. 未验证 / 已知限制

- **阴影不可见**：`shadow_enabled = true` 已设且已序列化，但 vision 报告看不到投射阴影。
  可能原因：物体尺寸太小（立方体 0.2 m、标尺厚 0.02 m）、方向光角度较陡、
  或默认阴影贴图分辨率/范围不足以呈现小物体阴影。**未定位，未修复。**
  对 T002/T007 验收无影响（不要求阴影），但记录在案。
- **画面仍属"灰盒"**：纯色材质、无贴图、无 AO/反射。这对测试场景是**合适的**，
  不代表最终画质。
- **性能未测**：无 FPS 数据。`forward_plus` 在 T600 4GB 上的表现属 P1。
- **视觉分析的置信度**：vision 模型对图像的描述属**语义判断**，不如像素统计客观。
  本文件的结论建立在"像素统计 + 几何自洽性 + 语义描述"三者**相互印证**之上，
  凡是三者不一致的地方（例如曾出现的"右侧带阴影长方体"）都已查出是无效输入（全屏截图含浏览器 UI）。

## 7. T009 的视觉证据与**一条新发现的工具限制**（2026-10-13）

T009（猫移动）用同一套方法留了 6 帧证据：`Art/Probes/t009_{ramp,low_ceiling,platform}_{tp,fp}.png`
（`tp` = 第三人称看姿态，`fp` = 猫自己的第一人称视角）。
工具：`tests/tool_capture_render.gd -- t009`（不能加 `--headless`）。

**新限制：视觉模型会漏"小而暗"的目标。** 低顶那张第三人称帧里，蹲姿猫只占约 150 px
（0.30 m 高物体在 1.7 m 处、45° FOV）且处在板下阴影中，视觉模型**两次**都回答"板下是空的"。
**没有据此下结论**，改用客观方法：

1. 同一机位拍"无猫 / 有猫蹲在板下"两张，逐像素求差：

```
DIFF|size=1280x720|sampled_changed=4593|bbox=(564,310)-(716,460)
```

→ 有 **152×150 px** 的区域确实因猫而变化（与该物体在画面中的理论尺寸一致）。

2. 把该区域裁出来单独提问，视觉模型才给出：
   「主体呈圆形/球状轮廓，深灰或深褐灰……很可能蜷缩的身体；**是的，存在**：右上方有紫色矩形板。」

**结论/规矩**：当主体小、暗或被遮挡时，**不要用"视觉模型没看到"当作"画面里没有"**；
先用"有/无主体差异像素"把客观边界定出来，再把差异区域裁出来交给视觉模型描述。
（与 §5 最后一条"像素统计比语义判断客观"同一条原则，只是这里多了一层"目标太小"的失败模式。）

**补充（根因之一其实是工具 bug，而不是模型）**：后来核对 MD5 发现，切换相机后 `tp`/`fp`
两张图**内容完全相同**（大小、哈希都一致），而日志里活动相机明明已经切换 ——
原因是**只 `await process_frame` 时读到的是上一帧**。修法是读像素前 `await RenderingServer.frame_post_draw`
（等 2 次），修完后三对图 MD5 全不同，且低顶那张第三人称帧视觉模型也**正常看到了蹲姿身体**
（"深灰褐色半球物体，顶部与紫色板底有明显空隙"）。
→ **规矩**：换机位/换视角后的两张图，必须先用 **MD5 或像素差**确认内容真的不同，再拿去判读；
"文件存在 + 名字不同"不代表内容不同（这一条已写入 `Docs/Commands.md` §8）。

**顺带记录**：lab 场景换猫后，默认捕获帧的 `CAP|active_camera=Camera3D` +
`CAP|camera_global_pos=(0.0, 0.440195, 0.0)` 正好等于"猫身体中心 0.34 + 眼高 0.10"，
是 T009 相机轴决策（`camera_offset_z` = 竖直偏移）的**运行时**旁证。
